# ESPAgent 现场演示与故障预案

## 1. 演示目标

现场演示不是功能越多越好，而是用最少步骤证明四件事：

1. 四个节点身份正确并在线。
2. 自然语言可以产生真实、结构化的跨节点结果。
3. Control 动作受到 Guardian 和本地安全边界约束。
4. 网络或单节点故障时，系统能明确失败而不是伪造成功。

推荐只演示三条稳定主链：`/help`、温湿度读取、状态灯控制。自动化作为加分项，前端作为可选观察面。

## 2. 比赛主机前置条件

当前主机工具以 Linux/WSL 为主：

- Python 脚本依赖 POSIX `termios`。
- 四块 S3 固定使用 `/dev/ttyUSB0-3`。
- `/dev/ttyACM*` 可能是 ESP32-P4，禁止作为 S3 烧录目标。
- 固件要求 ESP-IDF `>=6.1.0,<6.2.0`。
- 飞书测试还需要有效 bot、chat id 和外部服务。

原生 Windows 当前不能直接运行大多数四串口测试。赛前必须在最终比赛主机上完成一次全流程验证，不能只确认代码能打开。

## 3. 硬件布置

| 端口 | 角色 | 建议外设 |
|---|---|---|
| `/dev/ttyUSB0` | Coordinator | 保持轻载，只接必要状态指示 |
| `/dev/ttyUSB1` | Sensor | AHT20、SGP30、BH1750、PIR |
| `/dev/ttyUSB2` | Control | WS2812、舵机、继电器/执行器 |
| `/dev/ttyUSB3` | Guardian | 不接复杂执行器，专注 policy/audit |

供电原则：

- 所有外设与 ESP32 共地。
- 舵机、灯带、继电器、风扇和音频功放使用独立电源。
- HC-SR05 Echo 必须分压或电平转换。
- 不让 ESP32 板载 3V3 承担大电流负载。

## 4. 赛前一天检查

### 4.1 固定版本

- 记录当前 commit：`git rev-parse --short HEAD`。
- 确认分支是 `agent-update`。
- 不在比赛前夜拉取新提交或升级依赖。
- 保存四块板已验证固件和完整 flash artifact。
- 保存前端 `package-lock.json`，不要临场升级 npm 包。

### 4.2 固定网络

- 准备主 Wi-Fi 和备用热点。
- 确认四板都连接同一可访问 broker 的网络。
- 确认飞书、LLM API 和 MQTT broker 没有过期凭据。
- 记录代理配置；不确定时不要临场修改全局代理。

### 4.3 固定端口

```bash
ls -l /dev/ttyUSB0 /dev/ttyUSB1 /dev/ttyUSB2 /dev/ttyUSB3
```

给 USB 线和板子贴实体标签。端口枚举可能因插拔顺序变化，不能只靠记忆。

### 4.4 运行角色检查

```bash
python3 tools/verify_roles_usb0_3.py --echo
```

预期：四项 PASS，node id、role 和 capability 分别对应 Coordinator、Sensor、Control、Guardian。

### 4.5 快速 Mesh 检查

```bash
python3 tools/stress_mesh_usb0_3.py \
  --rounds 1 --interval 1.5 --settle 25 --quiet
```

预期：命令成功排队、Sensor/Control 收到并执行、Guardian 有 decision/audit、无 crash pattern，最终 `RESULT: PASS`。

## 5. 开机检查清单

按顺序确认：

- [ ] 四块板、外设、电源、共地正确。
- [ ] USB0-3 全部存在，未误用 ACM。
- [ ] 角色检查 PASS。
- [ ] `config_show` 角色与 node id 正确。
- [ ] `wifi_status` 显示已连接和有效 IP。
- [ ] 四板出现 `MQTT connected`。
- [ ] USB0 出现 Feishu WS connected。
- [ ] USB3 `stateboard_show` 能看到节点状态。
- [ ] `heap_info` 没有异常低内存。
- [ ] 日志中无 `Guru Meditation`、`Backtrace`、stack canary。
- [ ] 前端若使用，MQTT 显示 connected 且 source 不是 `local_mock`。

## 6. 标准演示流程

### 演示 1：确定性入口

发送：

```text
/help
```

预期：直接返回 slash command 帮助，不调用 LLM。

讲解：

> 这条命令证明系统保留了确定性控制面。即使 LLM 或外部 API 暂时不可用，基础诊断和明确命令仍能工作。

### 演示 2：Sensor 跨节点读取

发送：

```text
请读取当前温度和湿度，并告诉我数据来自哪个节点。
```

观察点：

1. USB0：请求进入、`mesh_send_command`、command id、queued。
2. USB3：收到 policy check，发布 allow/deny 和 audit。
3. USB1：收到 Sensor role command，调用温湿度工具。
4. USB0/飞书：收到结构化结果并回复真实读数。

讲解：

> 这条链不是 Coordinator 自己伪造一个温度，而是把请求交给 Sensor，结果携带结构化状态和关联 ID 返回。

### 演示 3：Control 安全执行

发送：

```text
/control set status light blue
```

观察点：

1. Guardian policy decision。
2. USB2 收到 Control command。
3. command queue admission 通过。
4. WS2812 物理变蓝。
5. timeline/OutputMessage 返回。

讲解：

> Guardian 决定请求是否允许，Control 再根据本地 busy、急停、重复 ID 和互锁状态决定现在是否能执行。网络授权不会绕过物理安全。

### 演示 4：自动化，可选

只在前三条稳定后演示。优先使用临时 workflow，不在现场留下持久规则：

```text
让控制节点的状态灯现在变蓝，10 秒后变黄，再过 5 秒变白。
```

讲解：

> LLM 只负责把自然语言转成有限步骤，真正的延时由 FreeRTOS workflow task 执行，不需要持续占用一次 LLM 会话。

边界：workflow 不跨重启恢复；步骤排队成功不能自动等同物理动作全部完成。

## 7. 前端演示

```bash
cd frontend
npm run server
npm run dev
```

预期：Node 服务在 4175，Vite 页面在 4173。

演示前确认：

- MQTT 状态为 connected。
- topic prefix 与固件一致。
- runtime skill source 是 `serial` 或 `proxy`，不是 `local_mock`。
- WebSocket URL 正确。

讲解时说“Web 控制台是观察与交互层”，不要说 demo 登录提供生产安全。

## 8. 故障矩阵

| 故障 | 先看什么 | 恢复动作 | 现场话术 |
|---|---|---|---|
| Wi-Fi 断开 | `wifi_status`、retry 日志 | 恢复 AP，必要时重新配置 Wi-Fi | “本地 CLI 仍在线，云端推理和公网 Mesh 暂停。” |
| MQTT 不通 | connect failed、四板在线状态 | 恢复 broker/network，等四板重连，再跑 1-round | “角色本地能力仍在，跨节点协作暂不可用。” |
| LLM 失败 | `llm_last_error`、HTTP code、heap | 检查 key、限流、TLS、网络 | “确定性命令仍可工作，开放式语言推理正在降级。” |
| Feishu 不通 | USB0 WS connect/disconnect | 检查凭据、网络，用 `inject_msg` 分离验证 Agent | “板端 Agent 可单独验证，故障位于聊天入口。” |
| Sensor 离线 | USB1 state/log | 恢复供电和 MQTT，重新请求 | “系统会返回超时，不会制造传感数据。” |
| Control 离线 | USB2 state/log | 恢复节点后重新下发 | “控制动作不会被虚假确认。” |
| Guardian 离线 | USB3 无 decision | 恢复 Guardian | “安全节点缺席时应 fail-closed。” |
| Coordinator 离线 | 无 Feishu/调度 | 重启 USB0 | “其他节点仍可采样和发布状态。” |
| 某传感器失败 | 驱动错误与 Mesh 日志分离 | 检查接线、供电、I2C 地址 | “通信可能正常，失败位于具体外设层。” |
| 串口被占用 | monitor/process、设备枚举 | 关闭重复 monitor，重新绑定 WSL USB | “串口是诊断面，不等于业务链停止。” |
| Bootloader loop | invalid segment/no bootable app | 使用预先验证的 full image 恢复 | “这是镜像/烧录层故障，不是 Agent 逻辑故障。” |
| 前端显示异常 | source、MQTT connected、API health | 修复 Node/MQTT；必要时关闭页面演示 | “页面已降级 mock，不把它当实时证据。” |

## 10. 烧录安全

- `tools/flash_roles_usb0_3.sh` 默认 app-only，适合迭代，但不会更新 SPIFFS。
- 首次部署或 SPIFFS 内容变化时使用 full/spiffs 模式。
- `ESPAGENT_ERASE_BEFORE_FLASH=1` 会擦除 NVS，可能丢失 Wi-Fi、API key 和密钥。
- 不把 S3 固件刷到 `/dev/ttyACM*`。
- 不在比赛现场临时运行自动选首个串口的通用 deploy helper。
- 保留一套已经验证的 full image 和恢复命令。

## 11. 失败时的回答方法

不要说“刚才只是网络不好”。按层定位：

```text
物理供电/接线
-> USB/串口
-> 节点启动和角色
-> Wi-Fi
-> MQTT
-> Guardian policy
-> Sensor/Control 工具
-> OutputMessage
-> Feishu/前端显示
```

推荐话术：

> 现在我们看到 Coordinator 已经生成 command_id，Guardian 也返回 allow，但 Control 没有执行日志，因此故障范围已经缩小到 Control 节点在线状态或本地 admission，而不是 LLM 理解或上游策略。我们先检查 USB2 的 state 和 emergency stop。

能这样分层定位，比演示完全不失败更能体现对项目的理解。

- 质量可靠的 USB 线和带独立供电的 USB Hub。
