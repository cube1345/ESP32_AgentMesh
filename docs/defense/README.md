# ESPAgent 比赛答辩资料入口

这套资料用于帮助第一次系统接触 ESPAgent 的队员，在较短时间内形成可以讲清楚、答得准确、现场不慌的项目理解。

它不是背诵稿合集。建议先理解系统的因果关系，再记关键数字和标准表达。评委追问时，可靠的回答永远是：结论、机制、证据、边界、下一步。

## 推荐学习顺序

### 第一轮：先能说清楚

1. 阅读答辩讲稿中的 30 秒和 2 分钟版本。
2. 记住四个角色：Coordinator、Sensor、Control、Guardian。
3. 能画出主链：用户消息 -> Agent Loop -> Guardian -> MQTT -> Sensor/Control -> OutputMessage -> 用户回复。
4. 记住一句核心原则：**推理可以不确定，执行必须有边界。**

### 第二轮：建立技术理解

重点掌握以下六个问题：

1. 为什么使用四块 ESP32-S3，而不是一块板？
2. 为什么选择 MQTT 和 FreeRTOS queue？
3. LLM 为什么不能直接操作硬件？
4. Guardian 和 Control 本地互锁分别解决什么问题？
5. 普通对话、跨节点命令、自动化 rule、workflow 有什么区别？
6. 哪些能力已经验证，哪些仍只是原型边界？

### 第三轮：练现场

1. 按演示手册走完整流程，不临场发明命令。
2. 每个演示都要知道预期物理现象和关键日志。
3. 人为断开一次网络或关闭一块板，练习定位与降级话术。
4. 两人交叉提问问答题库，回答必须在 30-60 秒内完成。

## 回答框架

评委提问后，按五句话组织：

1. **结论**：先直接回答问题。
2. **机制**：说清使用了哪个模块、协议或安全层。
3. **证据**：给出真机现象、日志、测试或源码位置。
4. **边界**：主动区分原型能力和生产能力。
5. **下一步**：说明怎样工程化完善。

示例：

> 当前 MQTT 链路还不是生产级安全通信。现阶段使用 1883 明文 broker 完成比赛原型验证，命令层具备可选 HMAC、Guardian policy 和 Control 本地互锁。真机已经验证跨板策略与执行链，但生产部署还需要私有 broker、TLS、ACL、设备身份和密钥轮换。

这类回答比“我们已经很安全”更专业，因为它同时说明了已有机制、证据和工程边界。

## 表述可信度标签

答辩材料使用四种标签：

- **已实现**：当前分支源码中存在并进入编译主路径。
- **已验证**：仓库记录或本次赛前真机测试证明运行成功。
- **当前边界**：源码存在限制，不能按完整产品能力宣传。
- **规划中**：设计方向或未完成工作，不能说成现有能力。

## 必须保持诚实的说法

你可以说：

- “项目团队实现了……”
- “当前代码采用……”
- “我们在赛前重新验证了……”
- “我主要负责现场系统理解、联调验证和答辩呈现。”

不建议说：

- “这部分代码是我亲自写的”，除非确实如此。
- “所有功能都已完成并验证。”
- “这是完全离线的本地大模型。”
- “已经达到量产级安全和稳定性。”

真正熟悉项目的表现来自能解释设计原因、数据流、失败模式和边界，不来自虚构个人贡献。

## 当前资料口径

- 分支：`agent-update`
- 基准提交：`ba6d08c`
- 固件目标：ESP32-S3，ESP-IDF `>=6.1.0,<6.2.0`
- 四板顺序：USB0 Coordinator、USB1 Sensor、USB2 Control、USB3 Guardian
- 当前代码事实：四个 S3 角色都满足本地 Agent Loop 启动条件，但每个节点最多只有一个串行 Agent Loop；Feishu/WebSocket 入口仍只在 Coordinator。
- 当前不应宣传：本地大模型、生产 MQTT 安全、完整 P4/Android UI、语音链、Gateway/OTA planning。

## 赛前最后原则

1. 不在比赛当天升级依赖、改角色配置或大范围重构。
2. 不依赖公网服务完成唯一演示，准备串口和确定性命令作为降级路径。
3. 不用前端 mock 数据冒充实时硬件数据。
4. 不把命令“已排队”说成物理动作“已完成”。
5. 不编造时延、吞吐、功耗、成功率或资源余量。
