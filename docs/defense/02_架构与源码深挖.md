# ESPAgent 架构与源码深挖

## 1. 项目本质

ESPAgent 不是在 ESP32 上运行完整本地大模型，而是一个 MCU Agent runtime：

- 云端 LLM 负责开放式自然语言理解和工具选择。
- ESP32-S3 负责消息接入、上下文、工具执行、存储、策略、安全和硬件控制。
- 常见请求优先使用确定性快路径，降低延迟、内存和模型随机性。
- 多节点通过 MQTT 交换结构化 command、policy、telemetry、timeline 和 OutputMessage。

硬件目标配置：

| 项目 | 配置 |
|---|---|
| MCU | ESP32-S3，240 MHz |
| Flash | 16 MB |
| PSRAM | 8 MB Octal，80 MHz |
| 框架 | ESP-IDF `>=6.1.0,<6.2.0` |
| MQTT 开发端口 | 1883 |
| WebSocket 固件端口 | 18789 |
| LLM max tokens | 4096 |
| Agent 最大工具迭代 | 10 |
| 系统 Prompt buffer | 24 KB |

## 2. 四节点职责

| 角色 | 用户可见职责 | 真实代码职责 | 故障后的影响 |
|---|---|---|---|
| Coordinator | 飞书/网页入口、调度、回复 | chat channel、LLM、deterministic routing、automation、Mesh dispatch | 用户入口和集中调度中断 |
| Sensor | 环境感知 | 周期采样、telemetry、只读工具、Sensor Mesh command | 环境读数超时，控制/审计仍可在线 |
| Control | 执行器控制 | 白名单动作、Guardian 二次确认、队列、急停、互锁、状态快照 | 不执行物理动作，感知/问答仍可工作 |
| Guardian | 安全策略与审计 | policy decision、approval、audit、StateBoard、watchdog | 控制应 fail-closed，不应绕过授权 |

当前代码中的一个重要事实：`espagent_role_runs_llm()` 对 Coordinator、Sensor、Control、Guardian 都返回 true。因此四种 S3 角色都可以启动本地 Agent Loop，但每块板最多只有一个串行 loop。Feishu 和 WebSocket chat channel 仍只在 Coordinator/communication 角色启动。

这不是“四个独立大模型进程”，而是“四个角色化 MCU runtime，必要时调用远程 LLM”。

## 3. 启动过程

入口 `app_main()` 很薄，只负责四阶段调用：

```text
espagent_app_init_subsystems
        -> espagent_app_start_local_services
        -> espagent_app_connect_wifi_or_onboard
        -> espagent_app_start_network_services
```

### 3.1 子系统初始化

主要顺序：

```text
NVS
-> ESP event loop
-> SPIFFS
-> event router / message bus
-> memory / cache / skills / dynamic extension
-> device registry / session manager
-> Wi-Fi / proxy
-> role-gated Feishu / LLM / scheduler / Agent Loop
-> role facade
```

顺序的意义：网络和 Agent 启动之前，消息、存储和工具基础必须已经可用。

### 3.2 本地服务

- 所有角色启动 serial CLI。
- Sensor/telemetry 角色启动 environment、presence 和 SGP30 monitor。
- Control/actuator 角色可启动 boot servo task。

### 3.3 Wi-Fi 与 onboarding

- 等待 Wi-Fi 最多约 30 秒。
- 连接失败时启动 captive onboarding AP。
- `app_main()` 随后返回，不继续启动 MQTT、Agent 和 chat 网络服务。
- 连接成功后启动 SNTP；Coordinator 可启动 admin portal。

### 3.4 网络服务

主要顺序：outbound dispatcher -> Feishu -> role service -> MQTT -> Agent Loop -> automation/scheduler -> WebSocket。

Coordinator 会等待 Feishu bootstrap 短暂取得进展，再启动较重服务，以减小内存高峰。

## 4. 消息与并发模型

### 4.1 为什么使用 queue

Feishu、MQTT、WebSocket callback 不应该直接进行长时间 LLM 或硬件工作。它们把消息快速写入 queue，由专用 task 消费：

```text
channel callback
    -> inbound queue
    -> agent_loop_task
    -> outbound queue
    -> outbound_dispatch_task
```

优点：

- callback 尽快返回，避免阻塞网络栈。
- Agent 上下文串行处理，避免同一会话并发污染。
- 消息所有权明确，`content` 在堆上分配并由消费者释放。

代价：

- 单节点对话吞吐受一个 Agent Loop 限制。
- queue 满时会丢弃或拒绝消息，需要日志和背压策略。

### 4.2 主要任务

- `agent_loop_task`：构建上下文、调用 LLM、执行工具、生成回复。
- `outbound_dispatch_task`：按 channel 发送 Feishu/WebSocket/system 回复。
- MQTT socket/publish task：连接、订阅、发布、结果缓存。
- Sensor monitor task：周期采集与 telemetry。
- `rule_task`：扫描持久化条件规则。
- `workflow_task`：执行有限多步延时任务。
- Lua/subagent/restore 等临时或后台任务。

## 5. Agent Loop

一轮消息的核心过程：

```text
pop inbound
-> slash command / deterministic fast path
-> system prompt + session history + memory
-> LLM chat tools
-> parse tool call
-> tool guard / sandbox / registry
-> tool result 回到 LLM
-> final text
-> session / trace / timeline / OutputMessage
-> push outbound
```

### 5.1 确定性路径

常见温湿度、控制灯光、slash command、自动化创建等请求可优先由规则解析和受限工具处理。

价值：

- 减少不必要的 LLM 调用。
- 避免模型选择相近但错误的硬件工具。
- 使比赛演示更稳定、行为更容易复现。

### 5.2 ReAct 路径

复杂请求由 LLM 在有限迭代内选择工具。每次工具执行结果重新加入 messages，模型再决定继续调用或输出 final reply。

ReAct 不等于无限自治：最大工具迭代为 10，工具集合受角色和 capability 过滤，具体执行还受 guard 与 sandbox 约束。

### 5.3 Subagent

`spawn_subagent` 是本板上的临时 FreeRTOS task，不是另一块 ESP32。它只开放搜索、天气、时间和有限文件工具，不能嵌套生成 subagent，也不能调用硬件或 Mesh 工具。

## 6. 跨节点 Mesh

### 6.1 Topic 类型

主要 topic 语义包括：

- `nodes/<node_id>/state`
- `nodes/<node_id>/telemetry`
- `nodes/<node_id>/events`
- `nodes/<node_id>/command`
- `roles/<role>/command`
- `agent/timeline`
- `security/policy_check`
- `security/decision`

### 6.2 Sensor 请求链

```text
Coordinator mesh_send_command
-> Guardian policy_check
-> policy allow
-> Sensor role command
-> schema / target / auth / dedup
-> read_temperature_humidity
-> espagent.output.v1
-> timeline + result cache
-> Coordinator reply
```

Sensor 请求通常是只读，风险较低，但仍应验证目标、Schema 和重复 ID。

### 6.3 Control 请求链

```text
Coordinator intent
-> action allowlist / sandbox
-> Guardian policy
-> optional HMAC
-> Control command
-> Guardian decision recheck
-> command queue admission
-> hardware tool
-> OutputMessage / control state / audit
```

Control 的 admission check 包括：

- emergency stop 是否锁存。
- 当前是否 busy。
- 可选硬件 interlock GPIO 是否闭合。
- `command_id` 是否重复。
- 动作是否属于允许的执行边界。

### 6.4 OutputMessage

OutputMessage 用统一结构描述来源、命令、状态和结果。它的价值是：

- 让 Coordinator、前端和 Display 使用同一结果语义。
- 让 timeline 和审计能关联请求与执行。
- 为异步等待、超时与重试提供基础。

当前边界：普通 Sensor/Control command 可以按 `command_id` 等待结果；`agent_task` 远端目前先发布“已进入本地 Agent Loop”，真正 LLM final reply 没有继续携带原 `command_id`，所以完整任务完成关联尚未闭环。

## 7. Guardian 与纵深安全

安全链不是单点，而是多层：

```text
Prompt 约束
-> role-visible capability
-> tool guard
-> sandbox
-> JSON Schema / 参数 allowlist
-> Guardian policy
-> optional HMAC
-> Control queue / emergency / interlock
-> audit / timeline
```

为什么 Guardian 和 Control 都要检查：

- Guardian 回答“这个请求是否允许”。
- Control 回答“当前物理状态是否允许执行”。
- 网络授权不能替代本地急停和接线互锁。
- 本地互锁也不能替代身份、权限和审计。

高风险命令可进入 approval queue，由 `approval_confirm` 或 `approval_deny` 处理，一次性 approval 消费后仍需通过 Control 最终检查。

当前安全边界：

- 开发 broker 默认是明文 1883。
- HMAC 只有配置 key 时启用，默认空 key 不签名。
- Guardian decision 还不等于 TLS、ACL 或设备身份认证。
- 前端 demo login 不是服务端安全边界。

## 8. 自动化

### 8.1 Rule

适合“如果湿度超过 60%，就把灯变红”之类持续条件：

```text
自然语言
-> automation_create_rule
-> /spiffs/automation.json
-> rule_task
-> Sensor 读取
-> threshold + hysteresis + cooldown
-> Guardian-gated Control action
```

特点：持久化、可跨重启恢复、后台周期运行。当前最大 8 条 rules。

### 8.2 Workflow

适合“现在变蓝，10 秒后变黄，再过 5 秒变白”：

```text
automation_create_workflow
-> temporary workflow_task
-> delay
-> sequential Mesh steps
-> finish / remove
```

特点：运行期、有限步骤、当前最大 8 个 workflow slot。workflow 不跨重启恢复，且步骤默认更接近“已排队”确认，不能一概说成物理动作全部完成。

## 9. 存储与分区

| 分区 | 大小 | 用途 |
|---|---:|---|
| NVS | `0x6000` | Wi-Fi、API key、运行配置 |
| OTA data | `0x2000` | 双 app slot 状态 |
| app slot 0 | `0x200000` | 固件镜像 A |
| app slot 1 | `0x200000` | 固件镜像 B |
| SPIFFS | `0x400000` | memory、session、skills、devices、automation |
| coredump | `0x10000` | 崩溃信息 |

大 Prompt、history、JSON 和部分 task buffer 优先使用 PSRAM，同时保留 internal SRAM 给网络、TLS 和需要 DMA 的区域。

## 10. Runtime Skill、Manifest 与 Lua

### Runtime Skill

Markdown skill 被存入 SPIFFS，为 Agent 提供领域操作指导。前端/Node 可以通过 HTTP proxy 或 serial gateway 管理 skill；默认串口安装单文件限制 4096 bytes。

### Manifest

简单 I2C、UART、Modbus RTU、SPI、ADC、GPIO 设备可以用 JSON manifest 描述。控制 manifest 需要 SHA-256 sidecar，并受到 role、risk、permission、cooldown 和 Guardian 限制。

CAN/TWAI、BLE GATT、I2S/PDM、1-Wire、RMT/IR、USB CDC、SDMMC 等复杂协议目前不能简单宣传为全部可执行。

### Lua

Lua 通过 `espagent.call_capability()` 调用已有 capability，不直接获得任意 GPIO/I2C 权限。因此 Lua 是受管扩展层，不是绕过安全的脚本后门。

## 11. 前端与显示

React/Vite 页面和 Node 服务聚合 MQTT、HTTP、WebSocket 与串口 Skill：

- Vite 开发端口：4173。
- Node API/WS：4175。
- Browser WebSocket：`/ws`。
- Dashboard、runtime skill 和 preferences 通过 API 获取。

当前边界：请求失败会回退 `local_mock`；`admin/admin123` 是演示账号，session 存在 localStorage。只有确认 MQTT 状态 connected、数据 source 不是 mock 时，才能把页面内容称为实时硬件数据。

## 12. 设计取舍

| 选择 | 收益 | 代价 |
|---|---|---|
| 四块 ESP32 | 物理职责和故障隔离，真实 Mesh 展示 | 网络、角色配置和时钟更复杂 |
| 同一固件 | 协议、安全和工具共用，维护成本低 | build-time profile 混刷可能改变角色 |
| MQTT | 轻量 pub/sub、状态和 timeline 易扩展 | 当前安全/QoS/网络依赖不足 |
| 串行 Agent Loop | 上下文一致，降低并发复杂度 | 吞吐有限 |
| Guardian 独立节点 | 授权与执行分离，可审计 | 增加一次网络往返和依赖 |
| 确定性快路径 | 稳定、省 token、减少幻觉 | 规则覆盖范围有限 |
| SPIFFS | MCU 上简单持久化 | 并发写入、磨损和异常格式化需谨慎 |

## 13. 当前最重要的工程债务

1. `sensor_mqtt.c` 同时承担 MQTT client、command router、policy/output cache 和 telemetry，职责过重。
2. `agent_task` 最终结果 correlation 未闭环。
3. ESP-IDF 权威约束为 6.1.x，但部分 setup/build 文档仍写 5.5.2。
4. Windows CRLF 会破坏 manifest SHA-256 sidecar 校验，应通过 `.gitattributes` 固定 LF。
5. 缺固件 C 单元测试、CI 和稳定的结构化测试协议。
6. 公网明文 MQTT、前端 demo auth 和设备身份不满足生产部署。
7. 缺统一的端到端时延、P50/P95、功耗和长期稳定性数据。
