# ESPAgent 评委问答题库

回答建议控制在 30-60 秒。先直接回答，再讲机制、证据、边界和下一步。

## 一、项目定位与创新

### 1. 这个项目到底解决什么问题？

它解决自然语言 AI 与真实硬件之间缺少可靠执行边界的问题。LLM 负责理解和规划，ESP32 runtime 通过工具、Schema、Guardian 和本地互锁把意图变成有界操作，并用结构化结果证明是否执行。

### 2. 核心创新是什么？

不是“聊天控制 GPIO”，而是把 Agent 的消息、工具、安全、自动化和多节点协作落到 MCU/FreeRTOS。亮点包括角色化同固件、确定性快路径与 ReAct 并存、Guardian 与 Control 双层门禁、OutputMessage 结果关联，以及自然语言到持久化 rule 的转换。

### 3. 这是 ESP32 本地大模型吗？

不是。完整 LLM 推理由远程 API 完成。ESP32 本地运行上下文、Memory、工具、策略、自动化、协议和硬件控制。TinyML 或本地小模型只能作为未来方向，不能把当前项目说成离线大模型。

### 4. 为什么不用树莓派？

项目目标是低成本、低功耗、贴近传感器和执行器的边缘节点。ESP32 更能体现资源受限条件下的 Agent runtime。代价是内存和并发受限，所以使用 PSRAM、有界 buffer、FreeRTOS queue 和确定性逻辑；不是说 ESP32 在所有方面都优于 Linux。

### 5. 为什么用四块板？

四板提供物理职责隔离和故障隔离：感知、执行、策略、协调不在一个节点。这样能演示真实跨节点协作，并减少单点代码直接获得全部硬件权限。代价是网络、时钟、配置和联调复杂度增加。

### 6. 四块板真的是四个 Agent 吗？

它们是四个角色化 MCU Agent runtime。当前代码允许 Coordinator、Sensor、Control、Guardian 都启动各自的单串行 Agent Loop，但它们不是四个本地大模型进程，也不是 Linux 式多进程 Agent 集群。Feishu/WebSocket 用户入口仍集中在 Coordinator。

### 7. 为什么同一固件，而不是四个工程？

协议、工具、安全和运维逻辑可以共用，降低四套工程的维护成本。角色由 build-time profile 和 capability 分化。当前局限是身份主要在编译期，镜像混刷可能改变角色，下一步应迁移到 NVS/Board Profile。

### 8. 项目名称里的 Mesh 是 ESP-MESH 吗？

不是。这里的 Agent Mesh 是应用层角色协作网络，主链使用 MQTT topic 和结构化消息。ESP-NOW 只是旁路 telemetry 能力，不是当前 Agent Mesh 的主通信层。

## 二、架构与数据流

### 9. 一条温湿度请求怎样完成？

飞书消息进入 Coordinator inbound queue，确定性路由或 Agent Loop 调用 `mesh_send_command`，请求 Guardian policy，允许后发往 Sensor role topic。Sensor 校验 Schema、目标、重复 ID 和可选签名，读取 AHT20，再发布带 command_id 的 OutputMessage，Coordinator 最终回复用户。

### 10. 一条控制命令怎样完成？

前半段同样经过 Coordinator 和 Guardian。Control 收到后还会重新核对 policy，进入本地 command queue，检查 emergency stop、busy、重复 ID 和可选硬件 interlock，最后才调用 WS2812/GPIO/servo 等白名单工具。

### 11. 为什么用 MQTT？

MQTT pub/sub 很适合低资源节点的 state、telemetry、command、result 和 timeline 解耦，也便于前端与显示端同时订阅。当前自实现客户端和公网 1883 只适合实验，生产需要私有 broker、TLS、ACL 和设备身份。

### 12. 为什么用 FreeRTOS queue？

网络 callback 只负责快速入队，LLM 和硬件工作由 task 消费，避免阻塞网络栈。串行 Agent Loop 也能保护上下文一致性。代价是 queue 容量和单 loop 吞吐有限，需要超时、日志和背压。

### 13. 什么是 OutputMessage？

它是跨节点结果统一结构，描述命令、来源、状态和用户可见结果。它让 Coordinator、timeline、审计和前端使用同一语义，并为 command_id correlation、超时和重试提供基础。

### 14. 所有跨节点结果都完整闭环了吗？

没有。普通 Sensor/Control command 可以等待结构化结果；`agent_task` 当前在远端任务刚进入本地 Agent Loop 时就发布同 command_id 的“已排队”结果，真正 LLM final reply 没继续携带该 ID，所以最终完成关联仍需修复。

### 15. 为什么有确定性快路径，还要 LLM？

确定性路径负责高频、结构明确、风险敏感的请求，稳定且省 token；LLM 负责开放式表达、任务理解和复杂工具组合。二者互补，避免“所有动作都赌模型是否选对工具”。

### 16. `spawn_subagent` 是另一块板吗？

不是。它是本板上的临时 FreeRTOS task，工具白名单非常窄，不能嵌套生成 subagent，也不能直接控制硬件或发 Mesh command。

### 17. Coordinator 是单点瓶颈吗？

用户入口和集中调度上是。其他节点能继续本地采样和发布状态，但 Coordinator 掉线后用户聊天与集中路由会暂停。下一步可做多 Coordinator、leader election 或入口故障转移，但这不是当前已实现能力。

### 18. `sensor_mqtt.c` 为什么这么重要？

它目前不仅做 Sensor telemetry，还承担通用 MQTT 生命周期、command router、policy/output cache 和 timeline，因此处于多条关键链上。这也是结构债务，后续应拆为 MQTT client、command router、policy cache 和 sensor telemetry。

## 三、安全与可靠性

### 19. 为什么不让 LLM 直接控制硬件？

LLM 输出具有概率性。项目原则是“推理可以不确定，执行必须有边界”。真正执行前还要经过 capability、tool guard、sandbox、Schema、Guardian 和 Control 本地安全检查。

### 20. Guardian 解决什么问题？

Guardian 把授权、审批和审计从执行节点分离，判断某动作是否符合角色、风险和策略。它降低了 Coordinator 或 Control 单点越权风险，但不是绝对安全证明。

### 21. 有 Guardian 为什么还要 Control 互锁？

Guardian 只能基于网络请求和策略授权，无法替代现场物理状态。Control 最终检查急停、busy、重复命令和硬件 interlock，解决“策略允许但此刻物理上不能执行”的问题。

### 22. HMAC 默认开启吗？

不是。只有配置 Mesh auth key 时才使用 HMAC-SHA256，并预留 current/previous key 轮换。空 key 是开发兼容模式，不能宣传为默认安全通信。

### 23. MQTT 目前安全吗？

实验环境使用公共 broker 和 1883 明文端口，不满足生产安全。命令层还有 Guardian、可选 HMAC 和本地互锁，但生产仍必须增加 TLS、认证、ACL、topic isolation、设备身份和密钥运维。

### 24. Guardian 掉线会怎样？

控制链应超时或 fail-closed，而不是跳过 Guardian。现场可以把这解释为安全优先的降级：感知和本地状态仍可工作，但需要授权的控制暂停。

### 25. 如何防止重复执行？

命令携带 command_id，接收端和 Control queue 都有重复检查。当前去重状态主要在内存，重启后不会永久保留，因此对生产级 exactly-once 语义还不充分。

### 26. 如何处理高风险动作？

Guardian 可以创建 pending approval，由 `approval_confirm` 或 `approval_deny` 处理；approval 一次性消费并绑定动作。即使审批通过，Control 仍执行本地安全检查。

### 27. 能完全防 Prompt Injection 吗？

不能声称完全防御。当前通过不可信内容提示、工具/路径 sandbox、角色能力和 benchmark 的 `must_not` 约束降低风险。下一步仍需更严格的数据来源标记、权限模型和安全测试。

### 28. Lua 会不会绕过安全？

Lua 不能直接获得裸 GPIO/I2C 权限，而是通过 `espagent.call_capability()` 调用已有 capability，因此仍受 sandbox、角色、Guardian 和 Control interlock 约束。

### 29. 前端登录安全吗？

不是生产安全。`admin/admin123` 等是演示账号，session 在 localStorage，Node API/WS 没有完整服务端鉴权。前端只能作为演示交互面，不能作为设备安全边界。

## 四、自动化与扩展

### 30. Rule 和 workflow 有什么区别？

Rule 是持续条件行为，保存到 `/spiffs/automation.json`，由 `rule_task` 周期扫描，可跨重启恢复。Workflow 是当前运行期的有限延时步骤，由临时 task 执行，不跨重启恢复。

### 31. 为什么自动化不一直让 LLM 思考？

长期保持 LLM 回合会消耗网络、token、RAM，也无法保证实时性。LLM 只把自然语言转成结构化 rule/workflow，之后由确定性 FreeRTOS 逻辑执行。

### 32. 如何避免阈值附近反复触发？

Rule 支持 hysteresis 和 cooldown。Hysteresis 防止数值在阈值附近抖动造成开关振荡，cooldown 限制两次动作的最短间隔。

### 33. 当前自动化容量多大？

配置上最多 8 条 rules、8 个 workflow slot。不要把配置上限说成大规模性能数据，实际稳定容量仍需压力测试。

### 34. Manifest 能支持所有硬件吗？

不能。简单 I2C、UART、Modbus RTU、SPI、ADC、GPIO 路径可执行；BLE GATT、CAN/TWAI、I2S/PDM、1-Wire、RMT/IR、USB CDC、SDMMC 等复杂协议仍应写专用驱动或处于规划状态。

### 35. Manifest 的安全怎么保证？

Manifest 有协议、role、risk、permission 和参数边界；控制类需要 SHA-256 sidecar，并仍经过 capability、Guardian 和 Control。SHA-256 只能证明内容一致性，不等同可信发布者签名。

## 五、硬件与资源

### 36. 目标硬件参数是什么？

ESP32-S3，CPU 240 MHz，16 MB Flash，8 MB Octal PSRAM 80 MHz。权威 ESP-IDF 约束是 `>=6.1.0,<6.2.0`。

### 37. 分区为什么这样设计？

两个 app slot 各 2 MB，为双镜像布局留空间；SPIFFS 4 MB 保存 memory、session、skills、device manifest 和 automation；另有 NVS、OTA data、PHY 和 coredump。

### 38. 如何控制内存压力？

大 Prompt、history、JSON 和部分任务 buffer 优先放 PSRAM，保留 internal SRAM 给 TLS、网络和 DMA；代码还限制 token、tool iteration 和缓存大小，并在 LLM turn 延后部分 MQTT housekeeping。

### 39. 系统时延和功耗是多少？

当前没有统一、可复现的端到端 P50/P95、吞吐和功耗数据，不能编造。可以说明已经做过内存与真机压力验证，下一步会拆分测量 LLM、Guardian、MQTT、工具和硬件各阶段。

### 40. 遇到过什么真实稳定性问题？

项目历史记录过 Feishu/MQTT 活动下的 timer service 栈溢出。修复方向是把重工作从 timer callback 移到 worker，并增加 timer task stack。这体现了 MCU 上 callback 必须短小的工程原则。

## 六、测试、应用与未来

### 41. 测试策略是什么？

分为 manifest 静态校验、benchmark dataset 校验、单板串口 smoke、四板角色验证、Mesh/Feishu 压测和日志 artifact。它更偏系统与真机测试，固件 C 单元测试和 CI 仍不足。

### 42. 已经验证了哪些能力？

仓库记录包括 AHT20 真机采集、湿度 rule 经 Guardian 控制 WS2812、slash `/help` 与 `/control`、Feishu/Mesh 压测、Lua USB0 7/7 和四角色 8/8 smoke。比赛前应在当前 commit 和实际硬件上重跑主链。

### 43. 日志匹配能证明硬件正确吗？

不能完全证明。日志回归能覆盖通信、调用路径和 crash，但对日志文案敏感，也不能替代物理测量。下一步应增加结构化 test event、request id 和必要的外部传感反馈。

### 44. 为什么没有 CI？

当前验证重度依赖四块真板和 Linux 串口，仓库还没有标准 CI。近期可以先把 manifest lint、benchmark `--validate-only`、前端 build 和 ESP-IDF build 放入 CI，真机测试放实验室 runner。

### 45. 项目适合什么场景？

适合智能空间、实验室/教育 AIoT、边缘设备编排和可审计硬件控制原型。价值是统一自然语言、策略与异构设备，不是单一传感器本身。

### 46. 相比传统规则引擎有什么优势？

LLM 降低自然语言配置门槛并处理开放表达，deterministic automation 保证长期执行，Guardian 提供风险约束。系统不是用 LLM 替代规则，而是让两者分工。

### 47. 当前最大局限是什么？

依赖远程 LLM；Coordinator 用户入口存在单点；生产通信和前端鉴权不足；角色身份主要在编译期；缺 CI、量化性能和长期稳定性数据；`agent_task` 结果关联未闭环。

### 48. 为什么最近删除语音、Gateway 和 OTA planning？

这是范围收敛：把资源和比赛风险集中到 Agent Mesh 主链，而不是继续维护不稳定、非核心能力。工程成熟度不仅体现在加功能，也体现在敢于删除无法可靠证明的功能。

### 49. 为什么还不能直接量产？

原型闭环已经形成，但量产还需要私有 broker、TLS/ACL、设备身份、密钥 SOP、可靠 OTA/回滚、真实鉴权、物理互锁验证、长期稳定性、性能/功耗数据和合规测试。

### 50. 下一步优先级是什么？

先修复 `agent_task` correlation、统一 ESP-IDF 6.1 和行尾策略；再做私有 MQTT/TLS/ACL、设备身份和前端鉴权；随后补 CI、结构化测试、P50/P95/功耗测试，并完成 P4/Android 实时显示绑定。
