# ESPAgent 一页速记表

## 一句话

四块 ESP32-S3 组成轻量 Agent Mesh：云端 LLM 负责理解，MCU 负责有边界、可审计的感知、控制和自动化。

## 核心原则

**推理可以不确定，执行必须有边界。**

## 四个角色

| 端口 | 角色 | 关键词 |
|---|---|---|
| USB0 | Coordinator | Feishu、WebSocket、LLM、dispatch、reply |
| USB1 | Sensor | AHT20、SGP30、BH1750、telemetry |
| USB2 | Control | WS2812、GPIO、servo、queue、interlock |
| USB3 | Guardian | policy、approval、audit、StateBoard |

P4/Android 是 Display Terminal，不是第四个 S3 角色。

## 主链路

```text
用户
-> Coordinator inbound queue
-> deterministic route / LLM ReAct
-> mesh_send_command
-> Guardian policy
-> MQTT role/node command
-> Sensor/Control
-> OutputMessage + timeline
-> 用户回复
```

## Control 安全链

```text
role capability
-> tool guard
-> sandbox
-> Schema / allowlist
-> Guardian policy
-> optional HMAC
-> emergency stop / busy / dedup / interlock
-> hardware tool
```

Guardian 管授权，Control 管当前物理状态。

## Rule 与 Workflow

| Rule | Workflow |
|---|---|
| 持续条件 | 有限多步延时 |
| 写入 `/spiffs/automation.json` | 运行期临时 task |
| 跨重启恢复 | 不跨重启 |
| threshold + hysteresis + cooldown | step + delay |

最多 8 rules、8 workflow slots。

## 必背数字

| 项目 | 数字 |
|---|---:|
| ESP-IDF | `>=6.1.0,<6.2.0` |
| CPU | 240 MHz |
| Flash | 16 MB |
| PSRAM | 8 MB Octal，80 MHz |
| app slot | 2 MB x 2 |
| SPIFFS | 4 MB |
| MQTT 开发端口 | 1883 |
| 固件 WebSocket | 18789 |
| Vite / Node | 4173 / 4175 |
| LLM max tokens | 4096 |
| Agent tool iterations | 10 |
| Prompt buffer | 24 KB |

这些是配置事实，不是性能结果。

## 三条稳定演示

1. `/help`：确定性入口，不调用 LLM。
2. “读取当前温湿度”：Coordinator -> Guardian -> Sensor -> OutputMessage。
3. `/control set status light blue`：Guardian -> Control admission -> WS2812。

自动化和前端仅作为加分项。

## 创新点

1. MCU 上的 Agent 执行 runtime，不是聊天转发器。
2. 同固件、四 profile、物理角色隔离。
3. Deterministic fast path 与 LLM ReAct 混合。
4. Guardian 授权 + Control 本地互锁。
5. OutputMessage/command_id/timeline 结果结构化。
6. 自然语言编译为 FreeRTOS rule/workflow。
7. Lua/manifest 扩展仍受 capability 和安全链约束。

## 已验证口径

- AHT20 真机采集。
- 湿度 rule 经 Guardian 控制 WS2812。
- `/help` 和 `/control` slash command。
- Feishu/Mesh 四板链路和压力日志。
- Lua USB0 7/7、四角色 8/8 smoke 记录。

比赛前应在当前 commit 上重新跑主链，历史记录不能替代赛前实测。

## 当前边界

- 使用远程 LLM，不是本地大模型。
- 四角色可启动本地单串行 Agent Loop，但不是四个独立大模型进程。
- `agent_task` 最终 command_id correlation 未闭环。
- 公网 1883 broker 不是生产安全。
- HMAC 默认空 key，不是默认开启。
- 前端 demo login 不是真实鉴权。
- Workflow 不跨重启。
- P4/Android 完整实时 UI 未交付。
- 语音、Gateway/OTA planning 已从当前分支删除。
- 没有可信统一的时延、吞吐、功耗数据。

3. 代码/日志/真机证据。
4. 当前边界。
5. 下一步。

## 故障分层

```text
供电/接线
-> USB/串口
-> 角色启动
-> Wi-Fi
-> MQTT
-> Guardian
-> Sensor/Control 工具
-> OutputMessage
-> Feishu/前端
```

## 高分句式

- “我们把不确定推理和确定执行分层。”
- “安全不是单个 Guardian，而是从 capability 到本地 interlock 的纵深边界。”
- “命令已排队、软件执行成功和物理效果完成，是三个不同证据层次。”
- “我们区分已实现、已验证和生产可用。”
- “删除不稳定的非核心功能也是工程收敛。”

## 绝对不能说

- ESP32 本地跑完整大模型。
- 四块板都是完整独立 LLM Agent。
- MQTT/前端已经生产安全。
- 所有硬件协议均可动态扩展。
- 所有动作都有完整最终结果关联。
- 编造延迟、功耗、成功率或剩余资源。
