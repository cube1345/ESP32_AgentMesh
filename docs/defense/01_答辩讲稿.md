# ESPAgent 答辩讲稿

## 一句话定位

ESPAgent 是一个运行在四块 ESP32-S3 上的轻量 Agent Mesh：它让云端 LLM 负责理解和规划，让 MCU 负责有边界、可审计的传感、控制和自动化执行。

## 30 秒介绍

> ESPAgent 是我们面向 AIoT 场景设计的四节点轻量 Agent Mesh。四块 ESP32-S3 使用同一套 ESP-IDF 固件，通过 profile 分成 Coordinator、Sensor、Control 和 Guardian。用户可以从飞书或 WebSocket 提出自然语言需求，系统先进行确定性路由或云端 LLM 推理，再通过 MQTT 下发结构化命令；Guardian 做策略裁决，Control 做本地互锁，最终结果以统一 OutputMessage 返回并进入时间线。它的重点不是让大模型直接控制 GPIO，而是把不确定推理和确定执行安全地连接起来。

## 2 分钟介绍

> ESPAgent 的目标，是把 LLM Agent 的执行面真正落到低成本 MCU 和真实硬件上。系统由四块 ESP32-S3 组成，使用同一代码库和不同角色配置。
>
> Coordinator 是用户入口和调度节点，负责飞书、WebSocket、LLM、任务路由和自动化创建；Sensor 负责温湿度、空气质量、光照和存在感知等数据；Control 负责 WS2812、GPIO、舵机和继电器等执行器；Guardian 独立负责 policy、审批、审计和节点状态观察。
>
> 用户消息进入 FreeRTOS inbound queue 后，每个节点最多由一个串行 Agent Loop 处理。常见温湿度、灯光和自动化请求优先走确定性路径，复杂请求才进入 LLM ReAct。跨板动作不会由 LLM 直接碰硬件，而是经过工具 Schema、sandbox、角色能力、Guardian policy、目标节点校验，以及 Control 的去重、busy、急停和可选硬件互锁。
>
> 对于长期条件任务，系统不会让 LLM 一直占用一次对话，而是把自然语言翻译成持久化 rule 或运行期 workflow，由 FreeRTOS 后台任务执行。这样既保留自然语言交互能力，又让真正的控制逻辑保持确定、可追踪、可恢复。
>
> 当前项目已经形成四板 Mesh、传感到控制、Guardian 门禁、自动化和串口回归的原型闭环。生产化方面仍需完善私有 MQTT、TLS、ACL、真实用户鉴权、标准 CI 和量化性能测试。

## 5 分钟完整讲稿

### 1. 问题背景

> 传统物联网系统通常依赖固定 App、固定按钮或预先写好的规则。LLM 能降低交互门槛，但如果直接让 LLM 输出 GPIO 操作，又会产生幻觉、越权和不可审计的问题。

> 因此我们关注的不是“怎么让 AI 随便控制硬件”，而是“怎样让自然语言理解进入一个有边界的嵌入式执行系统”。

### 2. 系统方案

> 我们把系统拆成四种职责。Coordinator 面向用户和 LLM；Sensor 面向环境数据；Control 面向执行器；Guardian 面向策略与审计。四块板使用同一固件，通过角色 profile 和 capability 控制启动服务及工具可见性。

> 选择四块板而不是单板堆功能，是为了体现职责隔离和故障隔离。Sensor 故障不会直接变成 Control 的错误动作；Guardian 与执行节点分离，也让授权和执行不在同一信任域中。

### 3. 一条请求如何执行

> 以“读取温湿度”为例。消息从飞书进入 Coordinator 的消息队列。系统识别这是一个常见传感请求后，优先走确定性 Mesh 路由，创建带 `command_id` 的结构化命令。命令先请求 Guardian policy，允许后发布到 Sensor 角色 topic。Sensor 校验 Schema、目标、重复 ID 和可选 HMAC，再调用本地 AHT20 工具。结果包装为 OutputMessage，并发布到 timeline 和结果缓存，Coordinator 再向用户返回真实读数。

> 以“把灯变成蓝色”为例，前半段相同，但目标是 Control。Control 在 Guardian allow 之外，还会检查 emergency stop、busy、重复 command_id 和可选硬件 interlock，然后才调用 WS2812 工具。

### 4. 为什么需要自动化

> 对“一直监测湿度，超过阈值就变红”这类任务，如果保持一次 LLM 会话等待，既浪费网络和 token，也不适合 MCU。因此系统把请求转换成 rule，保存到 `/spiffs/automation.json`，由 FreeRTOS `rule_task` 周期读取 Sensor 数据，执行阈值、hysteresis 和 cooldown 判断，再走同样的 Guardian-Control 链路。

> 多步延时动作使用临时 `workflow_task`。Rule 可以跨重启恢复，workflow 当前只存在于本次运行期，这是我们主动区分的边界。

### 5. 创新点

> 第一，系统不是聊天转发器，而是在 MCU 上整合了消息总线、Agent Loop、工具注册、Memory、自动化和硬件执行。

> 第二，采用“LLM 理解 + 确定性快路径 + 有界执行”的混合架构。常见动作不依赖模型随机选择工具，复杂语义仍可由 LLM 处理。

> 第三，引入独立 Guardian 和 Control 本地互锁，形成授权与执行分离的纵深安全结构。

> 第四，用 OutputMessage、command_id 和 timeline 把自然语言任务与结构化执行结果连接起来，便于追踪和显示。

> 第五，把长期自然语言任务编译为 FreeRTOS rule/workflow，让 Agent 从“对话”进入“持续运行”。

### 6. 验证与边界

> 项目已经记录了 AHT20 采集、湿度规则经 Guardian 控制 WS2812、飞书 Mesh 路由、slash command 和 Lua 多角色 smoke 等真机验证。主机工具还能检查四板身份、执行 Mesh 压测并保存日志。

> 但我们不会把原型能力说成量产能力。当前 MQTT 使用开发环境的 1883 broker，HMAC 需要显式配置，前端登录仍是演示级，固件缺少完整 CI 和性能基准。下一阶段优先做私有 broker、TLS/ACL、设备身份、结构化测试事件和 P50/P95/功耗测量。

## 推荐现场演示串词

### 开始前

> 现在四块板分别承担协调、感知、控制和安全策略职责。我们先用角色检查确认每块板的身份，避免把错误固件或端口当成系统问题。

### 演示 `/help`

> `/help` 不调用 LLM，直接由确定性命令层响应。这证明系统不是所有操作都依赖云端推理，也为断网诊断保留了稳定入口。

### 演示温湿度

> 这条请求会从 Coordinator 经 Guardian 到 Sensor。请关注三个证据：Guardian 的 policy decision、Sensor 的真实读取日志，以及带相同 command_id 的结构化结果。

### 演示状态灯

> 控制链比传感链更严格。除了 Guardian allow，Control 还执行本地队列、急停、重复命令和互锁检查。即使上游 LLM 出现不合理建议，本地节点仍有最后执行边界。

### 演示自动化

> 这个条件任务不会让大模型持续在线。LLM 或确定性解析只负责把自然语言转换成 rule，之后由 FreeRTOS 任务持续执行，因此更适合嵌入式系统。

## 高分表达

- “我们不是让 LLM 直接控制硬件，而是让 LLM 进入一个确定性执行框架。”
- “Guardian 解决授权问题，Control 本地互锁解决最终执行问题，两者不能互相替代。”
- “同一固件降低维护成本，角色 profile 提供职责分化；当前 build-time 身份也是下一步需要迁移到 NVS 的工程债务。”
- “OutputMessage 的价值不是格式好看，而是给跨节点结果提供统一语义和 correlation 基础。”
- “Rule 是长期、持久化行为；workflow 是本次运行期的有限步骤任务。”
- “我们区分代码已实现、真机已验证和生产可用三个层次。”

## 绝对不要说

- “大模型运行在 ESP32 上。”
- “四块板都是完整、独立的大模型 Agent。”
- “所有跨节点任务都已经完整二次回灌 LLM。”
- “命令排队成功等于硬件动作完成。”
- “MQTT、前端登录和 HMAC 已经达到生产安全。”
- “P4/Android 显示端已经完整交付。”
- “已放弃的高负载扩展链路仍属于当前展示能力。”
- “我们的延迟、吞吐、功耗或成功率是多少”，除非赛前刚完成可复现实测。
